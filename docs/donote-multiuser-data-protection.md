# DoNote 多用户与数据保护设计

> 更新日期：2026-10-16（Asia/Shanghai）
> 状态：设计与实施计划；本文所述目标功能尚未实施。
> 执行分工：[智能体团队模块化实施与试行计划](donote-team-implementation-plan.md)。
> 核对基线：提交 `c704cea` 及当前工作区已有的前端改动。
> 适用场景：私有自建、管理员受控开户、个位数至几十名用户。

## 1. 目标、边界与实施顺序

本次演进将环境变量密码认证替换为可管理的账户与可撤销会话，同时保持个人剪贴板的数据隔离。用户应能查看登录设备、撤销远程设备，并按需将文本标记为敏感内容。

实施顺序为：

1. 修复备份覆盖范围，完成迁移与恢复工具。
2. 引入账户、密码哈希、服务端会话及 HTTP/Socket.IO 一致鉴权。
3. 接入必要的登录、用户管理和设备管理界面，完成安全切换。
4. 增加敏感文本加密、临时设备策略和存储配额。
5. 账户上线阶段同时交付 TOTP 与严格登录策略；附件加密、WebAuthn 和定向共享根据需求继续增强。

本阶段保持原生前端、Express 和单实例部署。消息继续使用 JSON，附件继续存放在磁盘；SQLite 负责账户、会话和审计。通过少量仓储接口隔离数据库驱动，不提前承诺无成本切换 PostgreSQL、S3 或多实例架构。

不开放公共注册。管理员可管理账户，但业务 API 不提供读取他人私有消息的权限。服务器运维人员仍可能读取文件、进程内存和密钥；服务端加密不能隔离拥有主机控制权的人员。

端到端加密暂不纳入本方案。它会改变服务端搜索和密钥恢复方式，但并不天然妨碍跨设备同步；如果以后采用，需要独立设计客户端密钥分发与恢复流程。

## 3. 风险分级与保护范围

| 优先级 | 问题 | 处理要求 |
| --- | --- | --- |
| P0：多用户切换前 | 密码长期留在浏览器、缺少独立会话撤销 | HttpOnly 随机会话 Cookie 替换密码凭据 |
| P0：多用户切换前 | 备份遗漏多用户目录 | 完整备份与恢复演练先于数据迁移 |
| P0：多用户切换前 | Cookie 认证切换后新增 CSRF、跨站 Socket 风险 | 明确 Origin、CSRF 和 Socket 握手准入 |
| P0：多用户切换前 | 服务端已撤销但客户端仍显示私有快照 | 服务端撤销、Socket 断开、本地数据清理共同验收 |
| P1：账户上线阶段 | 无用户生命周期、设备列表和审计 | 管理员账户管理、会话管理与审计 |
| P1：账户上线阶段 | 代理限流共用桶、认证状态可能被缓存 | 可信代理配置、组合限流、认证响应 no-store |
| P1：数据保护阶段 | 无配额、磁盘消耗缺少约束 | 全部写入路径的资源限制与并发控制 |
| P1：数据保护阶段 | 敏感文本明文落盘或进入快照 | 可选加密、独立解锁、禁止敏感明文持久缓存 |
| P2：按需增强 | TOTP、附件加密、定向共享 | 独立设计与验收，不阻塞基础账户切换 |

保护目标包括：跨用户越权、凭据重放、可撤销会话、离线数据泄露和备份恢复。以下边界必须如实告知：

- 撤销会话只能阻止后续访问，不能删除已经下载、复制或截图的内容。
- HttpOnly 能降低 token 被脚本直接读取的风险，不能阻止 XSS 在当前页面内代用户操作。
- 服务端字段加密保护“数据文件泄露但密钥未泄露”的场景；数据和密钥一起失守时不成立。
- 浏览器关闭和 Cookie 失效不保证本地内容被物理擦除；共享设备默认不持久保存私有快照。

## 4. 目标架构与存储边界

```text
浏览器（同源 Cookie，内存私有状态）
    │ HTTPS / Socket.IO
    ▼
Nginx（TLS、来源与代理边界、auth_request）
    │ 仅内部网络
    ▼
Express + Socket.IO（统一 session 校验与用户身份）
    ├── 账户仓储 ── SQLite：users / sessions / audit_log
    ├── 消息仓储 ── users/<uuid>/messages.json
    ├── 附件存储 ── users/<uuid>/uploads/
    └── 加密模块 ── 独立挂载的密钥
```

### 4.1 技术选择

- SQLite 使用 `better-sqlite3`，启用外键、WAL 和合理的 busy timeout；schema 用有版本的迁移管理。
- 密码采用 Argon2id，每次哈希自动生成随机 salt，参数按部署硬件压测后确定；登录并发受限，避免耗尽内存。
- 会话使用至少 32 字节的密码学随机 token；数据库只保存 SHA-256 哈希，token 仅通过 Cookie 传递。
- 敏感文本采用 AES-256-GCM；每次加密生成独立随机 nonce，认证 tag 必须验证。
- 账户、会话和审计通过小型仓储接口访问，业务路由不直接拼装 SQL。

`better-sqlite3` 和 Argon2 都涉及原生依赖。实施时选定仍受支持的 Node LTS，更新 CI 和容器基线，并验证目标 CPU、Alpine/musl 或 Debian/glibc 镜像构建。多阶段构建需保持编译和运行环境 ABI 一致，不能仅凭本地安装成功判断可部署。

### 4.2 JSON 与数据库之间的一致性

SQLite 事务不能原子提交 JSON、附件与数据库三方状态。第一阶段采用以下约束：

- 按用户串行化消息写入，保持现有原子文件替换。
- 账户状态和会话在数据库事务内更新；文件清理使用可重试任务和状态记录。
- 删除账户先禁止登录、撤销会话，再进行可恢复的数据清理；不能先删目录后更新账户。
- `storage_bytes` 是可核对的统计值，不能单独充当配额的权威来源。
- 多实例部署不在此方案范围；扩容前需替换内存状态、文件写入锁及 Socket 撤销通知机制。

## 5. 账户生命周期与权限

### 5.1 身份模型

- 用户主键为不可变 UUID，目录使用该 UUID，不使用可变用户名。
- `username` 用于登录，先规范化再做唯一性校验；大小写规则固定并写入测试。
- `display_name` 可修改，不参与权限判断。
- 角色为 `admin` 和 `user`。所谓“子账户”是管理员创建的独立账户，不继承管理员的数据访问权限。
- 账户状态为启用、禁用、软删除；物理清理另有任务状态。
- 初始管理员通过一次性初始化命令创建；仅允许数据库尚未初始化时执行。密码从交互输入或受限文件传入，避免出现在命令行参数和日志中。

### 5.2 生命周期规则

| 操作 | 会话处理 | 数据处理 |
| --- | --- | --- |
| 创建账户 | 不自动签发会话 | 创建用户目录 |
| 修改密码 | 撤销全部旧会话；如需保留当前设备，重新签发新会话 | 私有数据保留 |
| 管理员重置密码 | 撤销目标全部会话，临时密码要求下次更改 | 数据保留 |
| 禁用账户 | 立即撤销全部会话并断开全部 Socket | 数据保留 |
| 启用账户 | 旧会话不恢复 | 数据保留 |
| 撤销一个设备 | 只撤销目标 session 并断开对应 Socket | 数据保留 |
| 撤销其他设备 | 保留当前 session，撤销其余 session | 数据保留 |
| 退出所有设备 | 撤销包括当前设备在内的全部 session | 数据保留 |
| 软删除账户 | 禁止登录，撤销全部会话 | 按既定保留期保留，界面说明期限 |
| 物理清理账户 | 保持不可登录 | 删除消息、附件和用户密钥；审计保留最少元数据 |

最后一个启用管理员不能被禁用、删除或降级。检查与更新必须在同一写事务中执行，避免并发操作把管理员数量降为零。

### 5.3 权限矩阵

| 操作 | user | admin |
| --- | --- | --- |
| 读写自己的消息、收藏、备注和附件 | 允许 | 允许 |
| 读取他人的私有内容 | 禁止 | 禁止 |
| 修改自己的密码、显示名 | 允许 | 允许 |
| 查看和撤销自己的会话 | 允许 | 允许 |
| 管理账户、重置密码、撤销他人会话 | 禁止 | 允许 |
| 查看系统审计 | 禁止 | 允许，敏感字段脱敏 |
| 修改自身角色或绕过最后管理员保护 | 禁止 | 禁止绕过保护 |

身份从 session 推导。消息查询始终限定 `owner_id = 当前用户` 或对应用户目录；跨用户资源请求统一返回 404。管理员路由没有授权时返回 403。

## 6. 数据模型与接口契约

### 6.1 SQLite 逻辑模型

下表是目标字段约束，实际 SQL 由版本迁移提供；不在设计文档中维护第二份可执行 schema。

| 表 | 核心字段 | 约束与索引 |
| --- | --- | --- |
| `users` | `id`、`username`、`display_name`、`password_hash`、`role`、`must_change_password`、`created_at`、`updated_at`、`disabled_at`、`deleted_at`、`storage_quota_bytes`、`storage_bytes` | UUID 主键，规范化用户名唯一，角色 CHECK；软删除后默认保留用户名，避免隐式复用 |
| `sessions` | `id`、`user_id`、`token_hash`、`device_label`、`ip_address`、`is_ephemeral`、`created_at`、`last_seen_at`、`idle_expires_at`、`expires_at`、`revoked_at` | token 哈希唯一、用户外键、按用户和有效期建索引；设备标签和 IP 只用于展示与审计 |
| `audit_log` | `id`、`actor_id`、`target_id`、`action`、`detail`、`ip_address`、`created_at` | 按时间和主体索引；actor 可为空，删除账户不能级联删除审计 |
| `schema_migrations` | `version`、`applied_at` | 迁移版本唯一 |

所有时间戳统一为 Unix 毫秒。审计记录登录、退出、会话撤销、账户管理、密码变更、敏感内容标记和解锁事件。禁止记录密码、token、Cookie、恢复码、正文和密钥。定义审计保留期，避免无上限积累 IP 和设备信息。

阶段 B 新增 TOTP、登录 challenge、操作授权、恢复码和安全事件所需表；阶段 C 才新增配额预留及内容加密相关结构，不提前创建未使用的安全状态。

## 7. HTTP、代理与实时会话

### 7.1 Cookie 与服务端期限

生产 Cookie 建议使用 `__Host-dn_session`，由服务端通过 `Set-Cookie` 写入：

```http
Set-Cookie: __Host-dn_session=<随机token>; Path=/; HttpOnly; Secure; SameSite=Lax
```

不设置 Domain。持久设备可附加受服务端上限约束的 Max-Age；临时设备使用 session Cookie、短绝对期限和空闲期限。浏览器可能恢复 session Cookie，因此关标签或关浏览器不作为立即失效保证。

每次受保护 HTTP 请求检查 token 哈希、账户状态、撤销状态、绝对期限和空闲期限。`last_seen_at` 可节流写入，但不得延迟撤销判断。API 未认证返回 401 JSON，前端统一转到登录界面。认证与私有 API 响应使用 `Cache-Control: no-store`。

本地 HTTP 开发可用单独开发配置和非 `__Host-` Cookie 名；生产启动必须校验安全配置，不能自动降级为不安全 Cookie。

### 7.2 CSRF 与来源校验

Cookie 自动携带后，所有写操作都需 CSRF 防护：

- 校验精确 Origin；缺失 Origin 时按明确的同源 Referer 或非浏览器客户端策略处理，不能直接放行。
- 使用与 session 绑定的 CSRF token，前端以自定义请求头提交；包括 multipart 上传和登出。
- 登录接口同样校验来源并限制 JSON Content-Type，避免登录 CSRF。
- GET 不修改业务状态。SameSite 是补充防护，不能代替 CSRF 检查。
- 密码和管理员高敏操作要求近期重新认证。

### 7.3 Nginx 与可信代理

保留 TLS、内部网络和 `auth_request`，改为校验 session Cookie：

- 新登录、公开能力接口必须在 Nginx 精确放行；`/api/auth/me` 等私有接口仍受保护。
- 删除基于 Base64 密码的代理头注入逻辑，透传原始 Cookie；业务应用自行读取并校验 session。
- 内部认证端点只接受配置允许的代理来源；额外代理共享密钥可作为纵深校验，不能代替 session 或用户身份。
- Nginx 覆盖来自客户端的身份和代理头，应用不信任客户端提供的 `X-User-Id`。
- `trust proxy='loopback'` 不能覆盖独立 Docker Nginx 容器。应基于真实部署选择受控代理地址/子网；若使用 hop 数，必须证明没有更短的直连路径。
- 保持 app 端口不对外发布。内部来源判断使用底层连接地址，不依赖可被代理设置改变的 `req.ip`。
- 登录采用可信客户端 IP 与规范化用户名组合限流，另有全局和并发限制；不能因信任任意 X-Forwarded-For 而允许绕过。

### 7.4 Socket.IO

浏览器同源 Socket.IO 请求自动携带 HttpOnly Cookie。客户端不读取 token；服务端从 `socket.handshake.headers.cookie` 校验 session，绑定 `socket.userId` 和 `socket.sessionId`，由服务端加入用户房间。

同时执行：

1. 精确 Origin 白名单，使用握手准入检查覆盖 WebSocket 与轮询；CORS 配置同步收紧。
2. 对带 Cookie 的浏览器连接按明确规则拒绝不受信任或缺失的 Origin；将来如支持原生客户端，另行定义认证契约。
3. 建立 `sessionId -> sockets` 和 `userId -> sockets` 索引。
4. 撤销单个设备时只通知并断开对应 session 的连接；禁用、密码重置、退出全部设备时断开用户全部连接。
5. 用定时检查及会话到期定时器处理自然过期。新的入站业务事件先校验，出站私有推送前也确认会话仍有效，不能只等下一次客户端请求。
6. 重连必须重新鉴权。撤销事件与断开都触发前端私有状态清理。

第一阶段仍为单进程。未来多进程必须广播撤销并同步失效状态，不能只依赖当前进程内索引。

### 7.5 登录强度与二次验证

二次验证分为两个独立环节：登录时确认身份，以及已登录后执行安全操作前再次确认。普通 session 不自动包含管理账号安全设置的权限。

| 模式 | 登录要求 | 适用与约束 |
| --- | --- | --- |
| 标准 | 用户名和密码 | 可选开启第二因素；未开启时明确提示防护较弱 |
| 严格 | 密码加已绑定的 TOTP，或按策略要求 WebAuthn 验证 | 每次新会话均验证，不提供长期跳过第二因素的信任 Cookie |
| 临时设备 | 使用账户已有验证要求，并缩短空闲/绝对期限 | 不持久保存私有内容；禁止降低安全策略和管理恢复方式 |

管理员在正式开放多用户前强制绑定第二因素。普通用户可选择严格模式，管理员可设定组织最低要求；用户不能降低到组织最低要求以下。WebAuthn/passkey 或硬件安全密钥作为更强选项，校验 challenge、Origin、RP ID 和 user verification；是否允许 passkey 单独登录由独立策略确定，不能因浏览器支持就静默替换验证流程。

启用 TOTP 时先重新验证现有身份，再生成待确认密钥，只有成功输入验证码后才启用。密钥加密保存；允许有限时钟偏差，服务端原子记录已使用时间步，阻止同一码重放。恢复码只展示一次、只保存哈希且单次消费。TOTP 不能防实时钓鱼，应在允许时推荐抗钓鱼的 WebAuthn。

密码正确但尚未完成第二因素时，只签发短期、限次数、用途为登录的 challenge，不生成完整 session，不允许访问消息、设备列表或 Socket.IO。失败统一提示，分别限制账户、来源、challenge 和全局并发，避免攻击者通过反复尝试绕过；不能采用无限期锁定账户让攻击者轻易拒绝本人登录。

### 7.6 踢出设备与安全设置的再次验证

持有 Cookie 的人可能只是拿到了一个未锁屏浏览器或被盗 session。因此以下规则由后端逐请求强制，不能只依赖弹窗：

| 操作 | 额外要求 |
| --- | --- |
| 退出当前设备 | 有效 session 和 CSRF，不要求再次输入密码，保证随时可退出 |
| 查看自身设备数量与脱敏摘要 | 有效 session；查看详细登录记录要求近期再次验证 |
| 踢出其他单个设备、其他全部设备或全部设备 | 新鲜的操作授权；已绑定第二因素时必须重新验证该因素，未绑定时重新验证密码 |
| 修改密码、绑定新因素、生成恢复码 | 验证现有认证方式；已有第二因素时不能只凭密码完成 |
| 关闭/替换第二因素、降低登录强度 | 验证现有第二因素并重新确认密码，或走明确的恢复流程；临时会话禁止 |
| 管理员重置账户、撤销他人会话、变更角色、清除第二因素 | 验证操作者管理员权限及其第二因素，并记录操作原因 |

操作授权建议不超过 2 分钟且单次使用，绑定 `userId + sessionId + action + targetSessionId/明确目标集合 + securityVersion`。服务端保存授权状态，事务内同时校验归属、账户状态、授权有效性并消费授权、撤销目标会话、写审计；只传 `verified: true` 或给 session 一个长期“已验证”标记均不合格。

登录时刚用过的 TOTP 不能在相同时间步重复消费；可等待下一验证码或使用另一个已登记因素。不要要求用户在几秒内连续提交同一验证码，也不要跨登录和安全操作 challenge 放开重放校验。

对仅有密码的账户，再输密码只能防“只偷到 Cookie”的攻击，防不住同时知道密码的人。界面应提示开启严格模式。若攻击者同时控制密码和第二因素，系统无法区分其与本人，需依靠独立恢复手段；不能承诺“永远不会被别人踢下线”。

会话列表、撤销和授权接口只允许操作自身会话；目标不存在或不属于当前账户统一返回 404。管理员走独立管理接口，不提供任意 `userId` 参数绕过。撤销“其他设备”的目标集合在授权时确认，不包括新并发创建且未展示的会话；需要清空全部时使用明确的全部撤销操作并递增账户会话版本。

### 7.7 登录历史、在线数量与安全事件

将“仍有效的登录会话”与“目前在线”分开展示：

- 有效会话：未撤销且未过期，可以重新访问。一个浏览器 profile 通常对应一个会话，多个标签页不是多个物理设备。
- 在线：最近收到经过认证的心跳或业务活动，例如 2 分钟内；Socket 连接数量不能直接等于设备数量。
- 离线但仍已登录：没有近期活动但会话仍有效，仍允许用户撤销。

设备页显示当前会话、设备/浏览器标签、首次登录、最近活动、登录验证方式、临时设备标记、脱敏 IP，以及在线和有效会话数量。设备信息与 IP 均不能证明物理设备身份；地域只是可选的粗略提示，不据此自动踢出。不要为查地域将完整 IP 发给第三方服务。

增加用户可查看的登录历史：成功、失败、第二因素失败、会话创建/过期/撤销、安全设置变更；展示时间、来源摘要和操作结果，失败记录不泄露其他账户存在性。记录至少区分 actor、目标用户、操作者 session、目标 session、验证强度和撤销原因，不记录凭据。完整 IP 访问受控，建议登录与安全记录默认保留 90 天，可由部署策略调整并定期清理。

新设备登录、批量踢出、密码/第二因素变更、恢复和管理员干预均生成安全事件。在仍在线的本人会话中提示，并保存可回看的事件；邮件等独立通知仅在配置可用时提供，不能以页面通知已送达为安全保证。普通用户无权删除审计；单机数据库审计不具备抵御主机管理员篡改的保证。

### 7.8 因素丢失与账号恢复

恢复流程不能成为比登录更弱的后门：

1. 有另一已绑定认证器时，验证该认证器后重新绑定。
2. 使用一次性恢复码时只获得短期恢复权限；按配置结合密码，不能直接获得无限期安全管理权限。
3. 密码和认证器均丢失时，由独立渠道核验后走管理员恢复；不能仅凭旧 Cookie、设备标签或 IP 恢复。
4. 恢复完成递增安全版本、撤销全部旧会话、旧恢复码、待完成 challenge 和操作授权，重新绑定并生成新恢复码。
5. 管理员恢复需操作者第二因素、原因与审计；恢复后要求目标用户设置新密码/因素，旧因素不能继续有效。

最高强度账户可选择禁止单个管理员直接清除因素，改用双管理员审批或离线恢复流程；启用前必须确认有足够管理员和可演练的应急路径，不能同时承诺“任何管理员都不能重置”和“单管理员随时救回”。管理员仍可按运维权限禁用账户或断开连接，这种管理权无法通过用户二次验证阻止，必须通过角色约束和审计管理。

### 7.9 必须补充的契约与测试

账户模型增加登录策略与 `security_version`；会话记录认证方式/强度及创建时的安全版本。对应阶段增加认证器、登录 challenge、单次操作授权、恢复码与安全事件持久化模型；TOTP 密钥加密保存，WebAuthn 保存公钥，恢复码只存哈希。

接口补充第二因素 challenge 验证、`POST /api/auth/reauth`、本人登录历史、安全策略设置及因素绑定/恢复。操作授权不能复用为登录 token、敏感内容解锁 token 或其他操作授权。

必须验证：只偷到 Cookie 不能踢出其他设备或关闭第二因素；只知道密码不能绕过严格模式；跨用户目标 ID 被拒绝；授权绑定目标、过期、重放及并发消费受控；已撤销 session 不能使用旧操作授权；恢复和策略变化撤销旧挑战；在线统计去重且超时转离线；所有安全变更可追踪。

## 8. 敏感文本加密

### 8.1 首期范围

先支持文本消息。图片和文件的“敏感”按钮在完整附件加密完成前不开放，避免用户误认为原图、缩略图或文件已受保护。

敏感文本包括正文和备注。消息类型、时间、收藏状态和密文长度等元数据仍可能可见；界面应说明保护范围。

### 8.2 落盘格式与密钥

敏感消息在 JSON 中保存版本化密文封装，例如：

```json
{
  "id": "<message-id>",
  "type": "text",
  "sensitive": true,
  "sensitiveAt": 1792076400000,
  "content": null,
  "remark": "",
  "encryptedPayload": {
    "version": 1,
    "algorithm": "aes-256-gcm",
    "keyId": "key-2026-01",
    "nonce": "<base64>",
    "ciphertext": "<base64>",
    "tag": "<base64>"
  }
}
```

加密载荷含正文和备注；AAD 绑定用户 UUID、消息 ID 和封装版本，防止密文被替换到另一用户或消息。每次重加密必须生成新 nonce。损坏、tag 验证失败或未知 keyId 时拒绝解密，不能回退为空文本或覆盖原密文。

首期使用独立挂载的 256 位服务器密钥及 keyId；不把密钥写进代码、数据库、审计或普通数据备份。信封加密按用户 DEK 与 KEK 分层作为后续增强。用户密码与内容密钥解耦，管理员重置密码不能导致数据不可解密。

密钥丢失会导致密文不可恢复。轮换保留旧 keyId 的解密能力，迁移任务可重试、可核验，确认全部重加密和备份恢复后再退役旧密钥。

### 8.3 访问与展示

- 列表、收藏、搜索、导出及 Socket 推送只返回锁定占位信息，不能通过通用序列化函数输出明文或密文封装。
- 搜索默认排除敏感正文和备注，可按“敏感”标记筛选。
- 解锁要求当前有效 session 和近期密码验证；服务端签发短期、绑定 session/消息/操作的授权，不接受客户端自报“已验证”。
- 解密响应 `no-store`，前端只在内存短时显示，超时、切换账户、页面隐藏策略或撤销后清理；不进入 localStorage、IndexedDB、Service Worker 或常规消息数组缓存。
- 备注修改、取消敏感、复制和导出均明确走敏感内容规则；解锁授权到期后不能凭旧 URL 读取。
- 标记敏感需要加密并持久化成功后再确认；清除服务端内存中的旧正文引用、浏览器快照和已渲染内容，并广播失效事件。
- 原有明文可能存在于历史备份、浏览器存储介质和文件系统旧块中，标记操作不能承诺追溯擦除。

建议接口：`POST /api/messages/:id/sensitive`、`POST /api/auth/reauth`、`POST /api/messages/:id/reveal`、`DELETE /api/messages/:id/sensitive`。具体请求体和错误码在实施时与测试一同确定。

## 9. 附件、配额与客户端残留

### 9.1 附件防护

保留现有路径逃逸检查、认证流式读取、下载处置和预览白名单。新 URL 不携带用户 ID、密码或 token；资源所有者由会话确定。

私有附件改用 `Cache-Control: no-store`，包括 Range 和错误响应；撤销后新的请求被拒绝。已经开始传输的数据不能召回，若需要中断在途传输，需维护 session 与活动流的映射并明确测试成本。

临时上传目录使用最小必要文件权限。失败、超时、客户端断连、配额超限和处理异常均清理临时文件，并配置陈旧临时文件清扫。仅凭目录路径不能断言其他进程一定可读，权限应通过部署验证。

附件加密作为后续独立阶段，必须同时覆盖原图、缩略图、预览副本、元数据、临时文件和 Range 策略；不能仅加密消息 JSON 中的路径。

### 9.2 配额规则

统计实际字节：文本、备注、原图、缩略图及文件。覆盖 multipart 和 JSON/Data URL 两种写入路径，同时限制单次请求、并发上传、消息数量和系统剩余磁盘。

Multer 在完整接收前不知道可靠的最终大小，Content-Length 只能作为提前拒绝提示。目标流程为：

1. 认证、CSRF、并发限制及可用配额预检。
2. 流式计数或受限临时落盘，超限立即停止并清理。
3. 以用户级串行化或数据库预留机制解决并发配额竞争。
4. 在提交消息前核对实际大小，提交成功后结算统计；失败释放预留并清理。
5. 定期对账真实附件与消息引用，修正崩溃造成的统计偏差。

不能通过“上传结束后读取 storage_bytes 并加一”来保证并发配额。

### 9.3 缓存与退出

Service Worker 继续仅缓存公开静态资源，不引入 API 或私有附件缓存。静态缓存无须按用户分区；版本升级仍更新 cache name 和资源版本。

账户切换的私有状态策略：

- 默认在服务端 `/api/auth/me` 验证成功后展示私有内容，不依据 localStorage 直接判定登录成功。
- 迁移时定向清理旧密码、用户 ID、过期时间和快照键，不使用无差别 `localStorage.clear()` 删除其他偏好。
- 第一阶段默认取消私有消息的长期浏览器快照。后续可信设备如恢复离线快照，必须按账户和版本隔离、设 TTL、先验证身份再展示，敏感内容始终排除。
- 临时设备不持久化任何私有消息，仅保留内存；sessionStorage 也不是关闭即保证销毁的安全边界。
- 退出、401、会话撤销、账户切换均清理消息、收藏、搜索结果、查看器、上传队列、Blob URL 和尚未完成的请求。
- 使用账户/认证代次标记或 AbortController 丢弃旧异步响应，防止退出后旧请求重新填充 DOM。
- 通过 BroadcastChannel 或同源存储事件通知其他标签页；页面从历史缓存恢复或重新可见时重新验证会话。
- 退出按钮先清空本端私有界面，再调用服务端撤销并处理失败。网络失败时不得声称服务端已退出，可在恢复连接后重试。

服务端退出清除新 Cookie，并清除旧 `wc_auth`；更新后的前端删除旧 localStorage 凭据。旧页面发来的密码请求应被拒绝，不能因为客户端尚未更新而兼容放行。

## 10. 备份、恢复与迁移

### 10.1 备份格式

先扩展现有脚本覆盖全部用户目录，再引入数据库。目标归档包含：

- schema/备份格式版本、应用版本、生成时间、用户映射及文件校验清单。
- 一致性 SQLite 副本。
- 根目录旧数据（迁移前）及全部 `users/<uuid>/messages.json`、附件和必要的迁移状态。
- 不包含临时上传、原始 session token 或加密主密钥。

SQLite WAL 模式下不能只复制主数据库文件；使用驱动在线备份 API 或 `VACUUM INTO` 得到数据库快照。数据库快照加上随后归档 JSON/附件，仍不是整体一致性备份。

当前规模推荐短暂停止全部写入者，等待 JSON 持久化完成，暂停清理任务，再对数据库、JSON 和附件做同一窗口快照。未实现全局写屏障前使用停机备份。备份失败不得删除上一份有效副本；任何必需文件缺失或打包失败必须报错，不能用 `|| true` 隐藏。

归档使用严格权限，可选或按运维要求强制公钥加密；解密私钥与应用内容密钥分别保管并验证恢复能力。保留周期与份数使用明确配置，不能把现有“14 份”误写成“30 天”。

### 10.2 恢复流程

1. 验证归档版本、校验和、目录结构，拒绝路径逃逸、危险链接和不支持的格式。
2. 停止全部写入者，创建并验证当前状态的完整回滚点；回滚点失败则中止覆盖。
3. 在独立暂存目录恢复数据库、JSON 与附件，执行 SQLite integrity/foreign-key 检查，核对用户映射和附件引用。
4. 按 keyId 确认所需密钥可用，用样本验证解密；不将密钥直接写入数据归档。
5. 保持应用停止，替换整套数据，正确处理旧 WAL/SHM 文件，避免旧旁路文件与新数据库混用。
6. 撤销恢复副本中的全部 session，再启动应用，要求所有设备重新登录。
7. 验证管理员、历史消息、附件、敏感内容与多用户隔离，失败则恢复完整回滚点。

撤销会话是防止备份中的旧会话重新变为有效；备份之后新建而恢复后不存在的 token 本来就应鉴权失败。

历史备份可能保留已删除账户或旧明文直到保留期结束。明确披露保留规则并定期在独立环境演练恢复，不将“归档能解压”作为恢复成功。

### 10.3 迁移步骤

迁移工具在实现和测试完成前不作为现成命令提供。

1. 盘点单用户及已有环境变量多用户模式；导出不含密码的用户与消息/附件数量清单。
2. 完成旧格式完整备份并验证恢复，固定回滚用旧镜像和配置。
3. 在停机窗口初始化数据库，通过安全输入创建首个管理员。
4. 生成并保存稳定映射：旧用户 ID → 新账户 UUID。单用户数据归明确指定的管理员，已有多用户数据逐个归属，不合并到同一账户。
5. 在暂存目录复制并核对数据，迁移旧消息模型与目录引用；不先删除源文件。
6. 工具支持 dry-run、逐项记录、失败重试和幂等重跑；以数量、校验和及抽样读取确认完整性。
7. 部署新后端、前端和 Nginx，移除旧密码鉴权及环境变量映射；统一切换会话协议，不并行接受两种身份体系。
8. 更新静态缓存版本，清理旧客户端凭据，要求重新登录。
9. 验收管理员保护、旧数据、附件、跨用户拒绝、会话撤销和备份恢复，再开放写入。

仅改用用户名密码时，不要求所有用户沿用旧共享密码。已有多用户账户可通过一次性迁移哈希或管理员分配临时密码过渡，完成后删除旧明文配置；具体策略在迁移演练时固定。

### 10.4 回滚边界

开放新系统写入前，可恢复旧镜像、旧配置和完整旧数据快照。开放写入后，直接恢复旧快照会丢失新数据，必须先冻结写入并保存新系统完整备份，再执行已验证的数据导出/回退策略。

数据库、JSON、附件、密钥版本和 Nginx 配置按整套状态回滚，不能只恢复数据库。回滚旧密码系统会重新引入旧凭据风险，应轮换旧密码并让用户重新登录。

## 11. 最小前端改动

用户明确约束：**前端不改现有样式，只补充新增功能对应的入口、表单、状态和交互。** 保留现有品牌、配色、字体、间距、按钮风格、主题、整体布局、时间线、搜索、卡片缩放和输入工作流，不进行视觉重设计或顺带美化。

新增界面优先复用现有组件与样式类。确需新增样式时，只为新功能添加局部作用域规则，不改变既有组件及全局样式；不得以安全改造为由重写样式文件。验收需对比改动前后的既有页面，确认原有视觉和布局保持一致。

在上述约束下增加以下必要界面：

| 页面/区域 | 改动 |
| --- | --- |
| 登录 | 用户名、密码、临时设备选项；统一错误提示；由服务端签发 Cookie |
| 用户菜单 | 当前显示名、修改密码、设备列表、退出当前设备、退出全部设备 |
| 设备列表 | 当前设备标识、最近活动、可脱敏 IP、撤销单个/其他设备 |
| 管理员区域 | 创建、启停、角色调整、密码重置、会话撤销、审计查询 |
| 敏感文本 | 标记、锁定占位、重新认证、短时展示和取消敏感 |

设备标签和 IP 仅供用户判断，不承诺精确识别物理设备。创建和重置操作不在普通消息流中展示密码。高风险操作显示明确结果，失败时不假装已完成。

## 12. 分阶段交付与验收

### 阶段 A：备份与迁移准备

交付完整多用户备份、恢复校验、迁移 dry-run、用户映射和回滚说明。

验收：单用户和多用户样本均可恢复；缺失附件、坏 JSON、路径逃逸、备份失败能被检测；重跑不重复迁移；原始数据保留；无真实密码进入输出或日志。

### 阶段 B：账户与可撤销会话

交付账户仓储、Argon2id、session Cookie、CSRF、代理来源规则、管理员保护、设备管理 API/UI、Socket 失效机制和前端清理。同时交付 TOTP、严格登录策略、操作级再次验证、登录历史及恢复码，管理员上线前强制第二因素。该阶段同时交付所需最小 UI，避免 API 完成但用户无法安全撤销设备。验收必须覆盖第 7.9 节所列的会话劫持与操作授权场景。

验收：

- 登录、过期、退出、单设备撤销、撤销其他设备、退出全部设备行为一致。
- 密码重置、禁用、删除后 HTTP 与已连接 Socket 均失效；其他用户和保留的当前设备不受影响。
- 不能通过消息 ID、查询 userId、Cookie、搜索、收藏、备注、下载、Range、预览和 Socket 越权。
- 第三方 Origin、CSRF 缺失、伪造转发头和旧密码鉴权请求被拒绝；合法代理仍按可信客户端限流。
- 最后管理员的并发禁用/删除/降级被阻止。
- 退出后刷新、后退、多标签页、旧异步请求和断网重连不会重新显示私有内容。
- Docker 与 CI 在选定 Node/CPU 环境完成依赖安装、构建和测试。

### 阶段 C：敏感文本、临时设备与配额

交付敏感文本加密和解锁、密钥配置与轮换、临时设备策略、存储资源限制和对账。

验收：密文不在列表/搜索/Socket/缓存中解密；备注、导出、复制遵循规则；错误密钥和篡改 tag 安全失败；标记操作失败可恢复；并发上传、断连、Data URL 与缩略图不会绕过配额；恢复演练能解密历史 keyId 数据。

### 阶段 D：按需增强

- WebAuthn/passkey 或硬件安全密钥：增加抗钓鱼认证选项及多个认证器管理；保持与既有恢复、操作授权和管理员最低验证要求一致。TOTP 基础能力已纳入阶段 B。
- 附件加密：覆盖完整文件链路并决定 Range、缩略图和临时明文策略。
- 定向共享：独立收件箱、授权、群组变更、转存和撤销语义；不恢复公开匿名分享。
- 更强密钥管理、可信设备离线缓存或外部数据库：由明确需求触发独立方案。
